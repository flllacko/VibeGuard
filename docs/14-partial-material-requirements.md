# 材料有缺口时，继续整理可读文字

日期：2026-10-15。此文记录已实现的范围，不代表整个 VibeGuard 项目完成。

## 用户看到什么

此前，S1 的前文里有一张未解析截图，服务连已经读到的文字也不整理。现在，满足来源检查的已确认任务，可以先展示文字候选：

> 用户原话：“我希望直接接入就能读取到这条对话的历史”
>
> 候选目标：接入后读取当前聊天历史。
>
> 当前结论：无法验证。
>
> 已取得：原始消息及逐字引用。
>
> 仍缺：非文字材料的解析、待定片段的解释、与本次要求绑定的执行证据。

范围、原文和图片缺口均保留。候选并未自动得到接受或通过。

## 放行条件

仅允许 `requirements_only` 任务先整理文字：

1. 用户已经确认范围，父原件、候选清单和确认原件重新核对一致。
2. 原文前缀、会话身份、消息结构和原始编号映射一致。
3. 父原件与确认原件有足够的分页及非文字内容账目。
4. 缺口全部能定位到带入前文的附件，数量与原件一致。

正文图片、缺页、未知历史、摘要、损坏映射、确认回复附带未知内容时继续阻断。旧确认无分页账目时仅保留范围选择，不能据此继续整理。

## 报告字段

| 字段 | 含义 |
| --- | --- |
| `requirementsStatus: partial_text_candidates` | 仅为可读文字生成的候选 |
| `textCoverage` | 消息及文字片段的处理去向，不是理解正确率 |
| `materialGaps` | 图片、缺消息或历史账目的具体缺口 |
| `unresolvedText` | 仍需解释的原话与原因 |
| `gapStage: material` | 整体还有材料问题 |
| `verdict: UNVERIFIABLE` | 证据不足，不能宣布完成 |

`resolutionComplete` 保持 false，冻结执行计划仍被拒绝。后续必须确认有效要求、生成验收标准并实际取证，不能把候选当作完成证明。

## 真实 S1 结果

用户明确同意将预览中的 29 条消息（7 条用户、22 条助手）发给 DeepSeek 官方 Flash。自动审批起初拒绝联网，取得这次具体外发许可后继续。未发送原图，密钥仅由环境变量用于认证；许可不扩大到其他聊天。

最终运行 `70142b91-e9e7-40ea-92b6-7e3630a90fc5`：

- 7 条用户消息都有处理去向，生成 3 条候选：真实平台实测、直接读取当前聊天历史、读取授权与完全访问的关系说明。
- “可以用 computer use”归为许可；已过去的备份限制、自主配置教学没有继续成为验收目标。
- 仍有 1 项图片和 8 个待定文字片段，整体为 `UNVERIFIABLE / material`。
- 所有候选原话与原始消息和偏移核对一致；原文、范围和缺口未改变；实际计划冻结门禁仍拒绝执行。
- 原聊天通过现有 MCP 直接读回结果。新处理逻辑在独立的新 MCP 进程运行，长驻旧进程需重载才能使用新行为。

“权限说明”是否仍属于该阶段，需要继续审视，当前未接受全部候选。此前的错误候选和失败试跑保留；本次调试样本不能当成语义准确率。

## 本次修正

- 程序按原消息序号稳定排列事件，保留同一消息内顺序并记录调整。
- 只规范化固定的同义标签，未知标签继续拒绝，不修改原话、要求或结论。
- 每个分块附同一主体阶段上下文，减少复活旧任务；助手交付文字只用于理解阶段，不作为完成证据。
- 宿主问题包装在用户答复里时，问题仍是助手引用，采纳它需要用户原答复依据。
- 私有 `model-attempts` 保存模型原始输出及用量，API 错误不再按格式问题重试。
