# VibeGuard：给 Codex 的实施计划

2026-10-18 执行增量：按[桌面与外部项目计划](17-desktop-and-external-project-plan.md)的 D1–D5 收敛后续交付：先增加外部项目契约和 Docker 运行，将已确认要求接回动态验收，再完成桌面审查/证据界面、扩展取证及 Windows `.exe` 安装包。下述历史 M 阶段及未完成能力继续保留；示例业务只是测试材料，不得每来一个任务就修改 VibeGuard 业务源码。

版本：0.1｜2026-09-27｜按里程碑实施，不将本文当作已完成记录。

## 1. 执行规则

先读 00-README、产品需求、技术设计和验收文档，再检查现有仓库。复用合理的已有代码，避免覆盖用户修改。当前目录只有文档时，从最小工程开始。

依据当前会话授权推进，不因每个可逆小步骤重复请求确认。需要账户、凭据、系统级依赖、宿主配置或对外操作时，说明具体缺口与影响；只暂停依赖它的工作。不得为了跑演示修改真实业务数据。

每个里程碑都有实际产物、验证记录和剩余问题。模拟模型响应只能证明接口能工作，不能证明真实模型正确；模拟执行输出不能作为验收证据。遇到工具失败时先保留真实错误，不改测试标准换取全绿。

每次完成一批工作，交付说明附一份可复制的 Git 提交说明，包含主要改动和验证结果。是否实际提交按用户指示执行。

第一版优先打通“原话 → 要求 → 实际执行 → 证据 → 结论”。不要先搭登录后台、团队管理、可视化大屏、模型投票或通用插件市场。

## 2. 建议代码结构

    VibeGuard/
      docs/                         本套设计与后续实施记录
      packages/
        core/src/
          contracts/                数据结构与运行时校验
          intake/                   原文接入与任务边界
          requirements/             要求版本、引用和覆盖
          planner/                  验收规划与 ModelGateway
          runner/                   工具、容器、预算与执行
          evidence/                 SQLite 与原始附件
          verdict/                  三态判定规则
          report/                   JSON、摘要与 HTML 模板
        cli/                        人与钩子的命令行入口
        mcp/                        三个工具的薄封装
        adapters/                   首个宿主和规范化对话导入
      examples/coupon-app/          可控演示应用与启动配置
      fixtures/
        conversations/              需求修改、取消、歧义等对话
        deliveries/                 固定的正确与缺陷交付
      tests/                        核心规则与集成测试
      evals/                        外部评估器与人工标准答案

这是建议结构，模块不必每个都独立发包。不要把外部评估标准答案放进运行时 Planner 能读取的材料中。

工程脚本至少提供 build、typecheck、test、test:integration、test:e2e、eval:smoke。名称可以调整，但在 README 中给出实际命令与前置条件。

## 3. M0：环境与范围核查

### 做什么

1. 检查仓库状态、Node/pnpm、Docker、浏览器运行条件、宿主版本和现有配置。
2. 用一个脱敏的真实任务样本调查首宿主：完整对话如何取得，回复结束事件是什么，报告如何显示，后台结果是否能投递。
3. 核查 Pi 与 MCP 的包名、版本、许可证和接口；记录依赖版本，生成锁文件。
4. 确认主模型 API、模型 ID、密钥环境变量名和初始预算。无真实凭据时可继续写契约与确定性执行部分，但真实模型阶段保持未验证。
5. 定义并冻结一个运行配置：启动、就绪探测、地址、测试数据准备、清理、允许资源。就绪检查失败应能产生明确报告。
6. 记录首版项目支持范围与宿主能力表。团队无法使用建议宿主时替换适配器，不重写 Core。

### 产物

- docs/implementation-status.md：环境、可用条件、缺口、阶段状态。
- docs/decisions.md：工程默认值的实际选择和依据。
- 一个规范化完整对话样本与演示运行配置。

### 完成条件

能说明材料怎样进入系统、哪里运行、结果怎样到用户手里。宿主尚不可用时明确标记，先推进 CLI 链路；不能宣称自动接入完成。

## 4. M1：确定性证据闭环

### 做什么

1. 建立 TypeScript 工程、契约、SQLite 存储和附件目录。
2. 实现 Runner 和 VerdictEngine 的最小垂直切片：手工编写检查计划，对演示 API 做真实请求。
3. 演示应用提供可复位的优惠券、订单与测试数据；分别保留正确版本和 149 元误优惠版本。
4. 每次运行记录快照、请求响应、订单观察值和退出状态。程序执行精确断言，生成三态结果。
5. 实现 CLI verify/report，输出 JSON 与简短终端报告。
6. 环境故意不可用时保留失败原因与已有记录，输出无法验证。

### 完成条件

实际得到一个已验证、一个验证失败、一个无法验证案例，关闭进程后还能读回证据。任何模型都不能通过提交 verdict 绕过 Runner。对应 A01、A06、A07、A09、A12、A15、A20。

这一阶段使用手写计划是为了单独验证执行与证据系统；M3 必须证明条件来自需求规划，不能把手写演示当成最终产品能力。

## 5. M2：完整对话与有效要求

### 做什么

1. 实现原始消息导入、任务边界与完整性记录。
2. 定义 ModelGateway，用 Pi 调用一个真实模型整理要求；提示版本与模型 ID 记录到运行中。
3. 模型输出包含原文位置、规范化要求、来源、变更关系和歧义。程序核对逐字引用与结构。
4. 实现增量更新：门槛 100 改 150 后保留一次使用和过期规则；取消功能不再作为必需项。
5. 对超长材料分块处理，保存每块覆盖；缺块或截断显示材料不完整，不能总体通过。
6. 显示来源区别：用户原话、现有约束、推导风险。材料中的引用和工具输出不能伪装成用户授权。
7. 用真实长对话回归“转述第三方方案但未采纳”的案例：引用存在不等于采纳。记录消息中引用边界、采纳状态、历史指令是否仍有效；不确定时保留歧义，不能生成必需失败项。

### 完成条件

通过短任务、长任务修改、取消、冲突和缺材料样本。错误引用被程序拒绝；难以确定的要求不会静默丢失。对应 A02～A05、A17、A18、A21。

## 6. M3：需求驱动的验收规划

### 做什么

1. 让 Planner 根据有效要求生成 Criterion 和 CheckSpec，关联来源及预期。
2. 实现最小通用断言：HTTP 状态与 JSON 字段、精确数值比较、受控数据查询、命令结果与测试发现情况。
3. 独立设计正反例与边界检查。例如 150/149、有效/过期、首次/再次，而不是照抄项目自带测试。
4. 计划冻结后再运行；遇到失败可补证或修复检查脚本错误，但不能不留记录地改变正确答案。
5. 每项要求有检查去向。无法设计可执行检查时明确输出无法验证，不用静态猜测替代。
6. 增加预算与取消控制；一轮补证后仍存在多种解释时停止猜测。
7. 分开生成可验收标准和项目执行步骤；项目运行配置只描述启动、接口、账号引用和数据准备，不硬编码本次业务预期。报告记录 material、requirement、plan、execution、evidence、currentness 缺口，并给出缺少的证据与下一步。

### 完成条件

给出此前没有固定计划的新表述和新门槛值，Planner 能据此生成相应检查；测试数值不得硬编码为 150/149。故意缺少反例、前置条件不成立、测试全部跳过时不能误报通过。对应 A06～A11、A16、A19。

## 7. M4：浏览器、隔离与可读报告

### 做什么

1. 接入 Playwright：打开结算页、设置测试商品金额、使用券、提交、读取用户可见结果并关联真实订单。
2. 保存 trace、关键截图、请求和操作结果。只有页面截图不能证明数据实际保存。
3. 为优惠券增加一个受控并发用例：两笔订单争用同券，统计实际获优惠订单数和券状态。
4. 完成受限运行配置：验证脚本与被测应用分离，证据目录不提供给应用写入，设定超时、资源和网络范围。
5. 生成本地 HTML 报告，包含原话、期望、实际、证据展开、限制和旧版本标识。
6. 配置脱敏与文件路径限制；拒绝任意文件读取和路径穿越。

### 完成条件

页面结果与订单记录能共同支持结论。正确、缺陷和无法运行的交付都可产生可读报告。第一版隔离承诺与限制在报告中可见。对应 A08、A13、A14、A20、A22、A24。

## 8. M5：MCP 与首个真实主动接入

### 做什么

1. 实现 verify_task、get_verification、read_evidence，复用 Core。
2. 工具只接已授权材料引用，不要求干活模型转述完整会话；报告读取限于授权项目。
3. 先实现宿主材料采集与主动验收，把用户的验收请求、真实任务原文和交付快照送入同一个 JobController。
4. 实现新交付检测、任务范围识别、重复事件去重和递归保护；普通回复不盲目运行全量测试。
5. 根据实测能力选择同步结果或后台任务与通知；适配 hook 的退出码，不造成意外阻断和自动修复循环。
6. 先验证主动验收与 CLI 复验使用同一数据结构和判定规则；后续自动扩展也复用它。
7. 安装与卸载接入仅修改明确的配置位置，备份原值并提供恢复方式，不覆盖其他插件配置。
8. 按[安装与跨平台接入设计](06-installation-and-integration.md)准备独立运行包与宿主接入入口；`connect/doctor/disconnect` 是待实现的目标体验，专用插件/连接器可作为不同宿主的包装。分开调查 Codex、Claude Code、Cursor、Qoder、WorkBuddy、豆包、ZCode、TraeCode，并维护其他主流平台候选池。先实测一个宿主的主动链路。
9. 自动验收作为 M5 后续扩展，默认关闭；用户开启后才按宿主事件执行新交付检查。单独实测关闭、启用、去重和递归保护，不作为当前主动模式实现的替代。

### 完成条件

先在真实宿主中完成一次“用户提需求 → 中途改需求 → Agent 交付 → 用户主动验收 → 展示原话与证据 → 用户要求修复 → 新快照复验”。MCP 与 CLI 使用同一 Core，对应 A25、A26 主动部分和 A28。自动模式另验 A23、A26 自动部分、A27、A29；未实现时明确标为未发布功能。

只有 CLI 或协议测试时，应如实称为原型，M5 的真实宿主主动链路未完成。主动链路完成也不代表自动模式已实现。

## 9. M6：产品评估与交付

### 做什么

1. 按验收文档运行固定缺陷、正确交付、缺环境三类案例。
2. 用同一交付物比较自报声明基线、固定测试基线、VibeGuard；保存原始记录。
3. 至少完成最小评估集；若要宣称普遍有效，再扩展隐藏样本和重复运行。
4. 记录错误通过、误报失败、无法验证、遗漏要求、耗时与总成本。
5. 完成安装说明、支持矩阵、真实演示记录、已知限制和故障恢复步骤。
6. 在第二个不同宿主复用同一 Core，验证对话、交付快照、触发与报告映射；第二宿主未完成前仅声称支持首宿主，不宣传“任意 Agent 一键自动验收”。

### 完成条件

所有发布必需案例通过；证据可以在新进程重新读取；一次演示同时展示发现缺陷、复验修复与诚实报告未知。外部结论与实际评估规模一致。

## 10. 可选阶段：Jev / Laya

仅在核心链路和成本记录稳定后开展。先旁路运行，不影响正式判定；选择确实频繁的小判断比较规则、当前主模型、Jev、Laya。

统计整个任务的总费用、延迟和补救调用，不只比较单次决策价格。降低必需检查覆盖或增加错误通过的方案不得启用。详细方法见验收文档。

## 11. 两人分工建议

| 方向 | 主要负责 | 共同约定 |
| --- | --- | --- |
| A：怎样验收 | 原话与需求版本、验收目标、风险和歧义、报告表达、评估标准 | 数据契约、三态语义、需求覆盖 |
| B：怎样拿证据 | 项目运行、HTTP/浏览器/数据库工具、证据存储、CLI/MCP/钩子、隔离与预算 | 运行身份、原始证据、故障分类 |

M1 共同做一条小闭环后再分开实现。双方使用同一批 fixture 和接口，避免最后才发现“条件”和“证据”接不上。

## 12. 每阶段结束时的交接格式

    阶段：M?
    状态：完成 / 部分完成 / 等待外部条件
    本次变更：文件、模块与行为
    实际验证：命令或操作、结果、运行编号
    证据位置：报告与原始附件
    未完成：具体缺口和原因
    下一步：下个最小动作

开发中同步更新 implementation-status.md。没有执行的测试写“未执行”及原因；不要把构建成功描述成产品验收通过。

## 13. 当前增量顺序（2026-10-19）

D1 固定交付与 D2 Docker 运行底座后，先实现 D3 的确认要求投影、通用 HTTP 规划、计划版本绑定与可读清单，随后让同一计划在运行器清理前执行并保存逐步证据。D3 的模型规划质量、实际功能取证、三态汇总和原聊天回传分别验证，不把完成规划称为闭环完成。原 Agent 优先的便利性细化不要求重做 Core 或先建大型桌面管理平台。
