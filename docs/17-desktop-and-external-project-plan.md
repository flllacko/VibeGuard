## 产品主线

VibeGuard 验收 AI 的本次任务交付：从原始任务对话整理当前有效要求，拆解验收标准，独立运行检查，逐项展示原话、实际结果和证据。示例业务只是验证验收器的测试材料，不决定产品支持的业务类型。

客户本轮要求：“最后给我一个exe程序这种形态”“就是要打通这些。能打通吗，你要怎么做”。既有的要求整理、真人确认、外部项目执行、隔离、三态评估和第二平台工作继续保留。

## 交付体验与技术路线

2026-10-19 调研后的体验细化：Windows 安装包继续保留，日常入口优先原 Agent；桌面用于接入、复杂审查、证据与历史。支持插件的平台优先以原生插件包装接入项，统一 MCP 与平台采集器仍由同一引擎使用。不要求用户每次另开 App 或复制对话；具体方案和未实现边界见[最终产品体验建议](20-product-experience.md)。这不改变 D1–D5 顺序。

- Windows 安装程序目标命名为 `VibeGuard-Setup.exe`，安装后打开本地任务验收台。安装包尚未生成。
- 页面覆盖平台连接、任务与原始材料、要求确认与自然修订、执行进度、证据及历史复验。Agent 是任务来源，不将新增聊天或多 Agent 调度系统作为本阶段交付。
- 原 Agent 中的主动 MCP 入口继续存在，与桌面入口使用同一 Core、要求版本、运行状态和证据。自动验收仍默认关闭，另行实测后启用。
- 桌面工程默认采用 Electron + TypeScript，复用当前 Node Core。选型是工程决定；依赖及运行时版本在实现前固定，验证 `node:sqlite`、模型 SDK、子进程和打包路径兼容。目标是随安装包提供必要运行时，用户无需另装 Node 或从源码启动。
- 桌面界面只调用受控的本地接口；运行项目、读取指定材料和写证据由独立执行层负责。不能让显示的项目文字获得任意本机命令能力。
- 连接成功、会话完整可读、工具记录可读、项目可执行分别自检。授权和安装包本身不能补齐平台未提供的材料。

## Docker 的职责

App 管理任务、审查与报告；Docker 运行本次允许执行的外部项目副本。读取聊天、查看报告和已有只读文件检查不要求 Docker。

首批动态验收默认需要可用 Docker。App 检测状态并给出操作指引，用户无需逐次手写容器命令。当前用户已经安装过 Docker Desktop，后续只检查是否能连接；未连接时保留需求整理与报告能力，依赖容器的检查明确无法验证。不得静默改为在宿主直接执行。

运行器固定交付快照、使用测试数据、设置资源及超时边界、记录启动与就绪状态并清理容器。待测项目不能挂载整个用户目录、宿主密钥、证据库或 Docker socket。依赖下载与测试网络按项目配置控制。Docker 降低影响范围，不承诺绝对安全或抵御任意恶意代码。

D4 的界面框架可与 D1–D3 并行，但不能用展示模拟报告代替执行能力。数据库只读检查按项目配置逐步扩展，不把任意 SQL 执行作为默认工具。

首批外部动态支持范围以 Node.js/TypeScript HTTP 项目为工程起点：有明确启动入口、可在容器运行、可复位测试数据。识别不准时让用户确认项目配置；具体任务标准从当次对话产生。随后扩展运行配置及项目类型，不承诺任意仓库开箱即用。现有文件任务能力继续保留。

## 验收门槛

1. 至少两个不同业务任务使用同一 VibeGuard 构建，任务之间只更换对话、项目配置和交付，不修改产品源码或人工补专用业务脚本。
2. 正确实现、有缺陷实现、环境不可用分别得到范围内已验证、验证失败、无法验证；结果逐项有来源，命令 exit 0 不能单独证明需求达成。
3. 代码或要求改变后生成新记录；旧报告可读但不能继承为当前已通过。
4. 用户可在界面纠正、取消、合并与补充要求，原话和修订记录保留；确认理解不等于完成验收。
5. Docker 不可用、项目启动失败、超时及取消均保留已有记录并报告缺口；待测应用不能写入证据目录，清理失败必须可见。
6. Windows 测试环境没有开发版 Node/pnpm 时，安装包仍能打开、执行已发布能力、重启读证据和卸载；需要 Docker 的能力单独自检。不满足时不得称为可交付安装版。
7. 第二宿主以应用内真实调用和材料核对验收；纯适配器测试不计为实际支持。
