# VibeGuard 产品需求

版本：0.1｜2026-09-27｜第一版开发基线。

## 1. 产品解决什么问题

AI Agent 会快速改动多个文件并宣布完成，但用户很难确认：需求是否漏掉、边界情况是否处理、原有功能是否被破坏，以及 Agent 到底有没有实际运行。

VibeGuard 是独立验收助手：根据用户当前有效要求，对交付物实施检查，用可追溯证据说明哪些得到验证、哪些失败、哪些无法判断。人决定是否接受交付。

核心价值是把用户要求、检查方法、实际结果连接起来。测试、浏览器操作、接口调用、数据库读取都是取得证据的方法。

目标用户是使用编程 Agent 的个人和小团队，尤其是缺乏时间或经验重新检查每项交付的人。第一版优先本地 Web/API 开发任务；长期可扩展到网页操作和数据处理。

## 2. 不可放宽的产品原则

1. 干活 Agent 可以提交交付声明，不能通过提交“pass”让 VibeGuard 通过。
2. 没有实际执行记录，不标已验证。静态代码推断应标明其证据性质。
3. 同一现象存在另一种明显解释时，增加对照检查；无法排除时输出无法验证。
4. 原话必须来自原始消息，模型生成的摘要不能伪装成用户原话。
5. 证据只支持明确范围内的结论，不能将一项通过扩大为整个功能正确。
6. 后续需求变更和代码变更使旧结论不能直接用于当前交付；旧报告保留。
7. 验收器也可能漏项，因此公开检查清单、覆盖缺口和运行条件，允许人复核。

## 3. 用户实际看到的效果

以下为模拟，不是已执行结果。

> 用户：给商城增加优惠券，满 100 元减 20 元，每张券只能用一次，过期券不能用。
>
> Agent：开始实现。
>
> 用户：门槛改成满 150 元，其他不变。
>
> Agent：已完成，修改了结算接口和页面，现有测试通过。
>
> VibeGuard：开始独立验收。优惠门槛采用你后来的要求：“门槛改成满 150 元，其他不变。”

系统自动在测试环境执行检查，随后显示：

| 依据 | 结论与实测结果 | 证据入口 |
| --- | --- | --- |
| 用户原话：“门槛改成满 150 元，其他不变。” | ✅ 150 元订单优惠 20 元，应付 130 元 | E01：请求、响应、订单记录 |
| 同一条原话 | ❌ 149 元订单仍优惠 20 元，实际应付 129 元，预期 149 元 | E02：请求、响应、订单记录 |
| 用户原话：“每张券只能用一次” | ✅ 首次成功，第二笔订单再次使用被拒绝，第二笔未获优惠 | E03：两次请求及订单记录 |
| 用户原话：“过期券不能用” | ✅ 过期券被拒绝；其他条件相同的有效券可用 | E04：有效期、测试时间和对照结果 |
| 补充风险检查，由“每张券只能用一次”推导 | ⚠ 并发检查未完成，无法确认同时提交时的行为 | 执行中止原因 |

150 元与 149 元的两次检查分别使用状态相同、未过期且未使用的券。不能把“因为券已用过而拒绝”解释成“门槛限制有效”。门槛这一要求的总体结果为失败。

用户展开 E02，可以看到原话所在消息、代码快照、前置数据、期望、实际结果、原始记录和复现步骤。

> 用户：修复 149 元也能优惠的问题，再检查并发。
>
> Agent：修改完成。
>
> VibeGuard：对新代码快照复验，生成新报告，保留上次失败记录。

第一版默认由用户发起修复。VibeGuard 不自动改业务代码，也不让验收失败造成无限循环。

## 4. 短任务与长任务

### 短任务

例如“增加登录功能”。提取原话，再列出从该要求推导的正常登录、错误密码、未登录访问等检查目标。没有明确提出的短信登录、第三方登录不能默认为必需功能。关键含义不清楚时提出少量有针对性的问题，其余可确定部分继续检查。

### 长任务

完整保存本任务对话，按新增消息更新需求。每条要求有稳定编号、来源和版本。阶段交付只检查已声明的阶段范围，其余要求显示“后续阶段”，不冒充已经验收；最终报告汇总当前全部有效要求。

用户说“这项先不做”，应保留取消记录；“先不做”与“永远不要做”不能无依据混同。一个会话里有多个任务时，明确本次任务边界，不能把整段会话里的所有历史愿望都算本次验收目标。

### 接入体验

用户安装并完成接入后，在原 Agent 中照常工作。第一版默认主动验收：用户说“用 VibeGuard 验收本次任务”，Agent 调用 MCP 工具；长任务允许用户明确发起阶段验收和最终验收。任务材料来自原始对话采集或导入，不能由干活 Agent 重新编写摘要代替。

自动验收作为随后可开启的扩展模式，默认关闭。用户启用后，宿主收尾事件触发候选检查，程序核对新交付和已有验收记录；普通聊天、等待用户答复和用户中断不自动等同于任务交付。干活 Agent 可以申请验收，不能决定验收通过。启用自动模式的入口尚待实现。

宿主支持时在原界面显示摘要；否则显示可访问的报告引用。不能承诺所有平台都有独立 VibeGuard 聊天气泡。自动触发、完整对话和结果回传三种能力需分别检测。

## 5. 功能需求

P0 为首版必须完成；P1 为核心稳定后的扩展；实验项不影响首版交付。

| 编号 | 优先级 | 功能 | 必须产出的效果 |
| --- | --- | --- | --- |
| F01 | P0 | 完整任务材料接入 | 保存角色、原文、消息编号、顺序、任务边界、材料来源与完整性声明；缺失明确提示 |
| F02 | P0 | 当前有效要求整理 | 新增、替代、取消和歧义可追溯；区分用户直接要求、引用的他人观点及是否明确采纳；原话可以定位且逐字核对 |
| F03 | P0 | 可验证目标拆解 | 先把每项有效要求拆成客观验收标准，再把标准变成当前项目可执行的检查；未覆盖要求必须可见 |
| F04 | P0 | 独立实际执行 | 能运行命令、调用 HTTP、做最小浏览器交互和读取允许的测试数据 |
| F05 | P0 | 证据保存 | 记录运行身份、代码与需求版本、环境、实际执行、原始结果和附件 |
| F06 | P0 | 三态判定 | 已验证、验证失败、无法验证；没有证据、工具失败或超时不能变通过 |
| F07 | P0 | 可读报告 | 每项有原话或明确的推导来源、验收标准、期望与实际、证据入口；无法验证时说明缺口发生在哪一步、缺什么证据、下一步怎么补 |
| F08 | P0 | 复验和历史 | 新版本新记录；旧结果标明适用版本；界面不将旧通过显示为当前通过 |
| F09 | P0 | CLI | 完整对话导入、验收、状态、读报告、诊断，支持机器可读输出 |
| F10 | P0 | MCP | 启动验收、读取状态与报告、按引用读取证据；不能上传一个 verdict 作为结果 |
| F11 | P0 | 一个真实宿主主动接入 | 实际演示用户提出验收请求、完整材料登记、MCP 调用与原话证据回传；同一请求可复用已有运行 |
| F12 | P0 | 运行与成本边界 | 配置预算、超时、取消；保留中途证据；统计模型 token、实际或估算费用 |
| F13 | P0 | 有依据的质疑 | 提醒冲突需求、无证据声明、观察结果与结论不符；主观偏好不被当错误 |
| F14 | P0 | 支持范围诊断 | 项目不能启动、缺凭据或缺对话时给出具体缺口，不能假装支持 |
| F15 | P1 | 风险驱动扩展检查 | 依据任务增加并发、性能、稳定性检查；推导项单独标识 |
| F16 | P1 | 更多宿主与运行配置 | Core 不改动即可扩展适配器；每个适配器公开能力表 |
| F17 | 实验 | Jev / Laya 优化 | 只有完整链路成本或速度改善且未恶化关键错误时才启用 |
| F18 | P0 | 可安装发行与接入说明 | 一个发行包提供 Core、CLI 和 MCP；首个适配器有可复核的连接、诊断与卸载流程；不支持自动接入的宿主可使用规范化对话导入 |
| F19 | P1 | 用户可开启的自动验收 | 默认关闭；启用后按宿主事件与程序规则检查新交付；去重、递归保护和报告回传须实测 |

并发能力在首版以优惠券演示的一个受控用例验证，不等于提供通用压测平台。登录属于补充验收样本，不要求第一版额外开发完整登录产品。

## 6. 需求与结论的边界

区分三种来源：用户明确要求；有来源的现有兼容约束；VibeGuard 推导的检查或风险。前两类进入必需范围；推导检查用于验证既有要求时可归入该要求，新增业务行为则必须单独列为建议，不能偷偷升级为客户要求。

报告按“**用户原话 → 当前有效要求 → 可验收标准 → 项目中的执行步骤 → 原始证据 → 结论**”显示。验收标准说清成功应是什么样，不预设特定工具；执行步骤才写调用哪个接口、准备什么测试数据、检查哪个字段。同一要求可以有多条必需标准，且每条标准都要有执行去向。

引用的第三方方案、Agent 的建议和用户提出的疑问，不能仅因为文字出现在用户消息中就变成已采纳的要求。需要识别引用边界及后续采纳、拒绝或暂缓；不明确时列为待确认，不用它作失败判据。历史阶段指令也要按任务边界和后续明确修改判断是否仍然有效。

例如“每券只能用一次”可以通过并发请求进一步验证；“退款后应自动退券”是额外业务规则，未约定时不能据此判需求失败。

敏感信息展示时允许明确标记的脱敏，并保留受保护的原文引用。不能把脱敏后的文本标为未经处理的逐字原话。

## 7. 报告状态规则

- 已验证：当前检查确实执行，前置条件成立，证据支持该检查的预期。
- 验证失败：实际观察与已明确的预期冲突。
- 无法验证：材料、环境、条件或证据不足，或存在未解决的歧义。
- 无法验证必须进一步指出缺口：材料缺失、要求含糊、计划未覆盖、执行未完成、证据不足或证据不适用于当前快照。计划里没有“一券再次使用”步骤属于计划缺口；计划有步骤但服务不可用属于执行缺口。
- 报告可列“当前有效要求 2 条：1 已验证、0 失败、1 无法验证”及各条必需标准的覆盖数。它是范围统计，不是完成概率；拆分粒度会影响分母，因此默认展示原始数量和缺口，不用单一百分比代替逐项结论。
- 已取消、后续阶段、运行中、旧版本属于范围或运行状态，不是第四种验收结论。
- 必需项任一失败，总体显示有失败；没有失败但有必需项无法验证或缺口，总体不能通过。
- 全部当前必需检查满足时，显示“本次范围内的必需检查已验证”，同时列出检查范围和未覆盖风险。

### 报告中的拆解示例

> 用户原话：“每张券只能用一次。”
>
> 当前有效要求：同一优惠券最多让一笔订单获得优惠。
>
> 必需标准 C1：有效券首次使用时，符合金额条件的订单获得优惠。
>
> 必需标准 C2：同一券第二次使用时，第二笔订单不能再次获得优惠。
>
> 执行方案：准备一张未使用的测试券，连续创建两笔符合条件的订单，再读取保存的两笔订单及券状态。
>
> 本轮结论：⚠ 无法验证。原因：计划缺口，尚未安排 C1/C2 的连续用券检查；已有证据：无；缺少证据：两笔请求、两笔订单和券状态；下一步：补全计划后在隔离测试数据上运行。

标准 C1/C2 来自这条要求的必要行为；具体接口路径、账号和数据准备来自项目配置。当前受控演示的人工计划确实写明“本轮未规划重复用券检查”，因此属于计划缺口；没有证据表明执行器尝试后失败。报告应显示这个区别。

## 8. 第一版不纳入的范围

不做自动修复循环、大型 Web 账户系统、团队计费、通用生产操作、任意仓库自动适配、无限制性能测试、区块链存证、正式安全认证、主观作品打分、多模型投票裁决。

证据可追溯是首版目标；“任何 Agent 都无法伪造”“软件绝对无 Bug”不属于可交付承诺。

## 9. 产品完成的可观察标准

用一段真实导入的需求变更对话，对有缺陷交付自动验收，发现 149 元误优惠，展示逐字原话及真实证据；修复后对新快照复验；故意断开环境时输出无法验证；用户关闭会话后仍能重新查看报告。具体测试矩阵见验收文档。
