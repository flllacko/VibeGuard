# VibeGuard 验收标准与效果评估

版本：0.1｜2026-09-27。以下是未来验收方法和目标，不是已取得的结果。

## 1. 验收交付包

首版应交付：可运行源码与锁文件、CLI、MCP、至少一个实测宿主的主动验收接入、演示应用及固定缺陷版本、结构化与可读报告、测试数据、评估脚本、安装/卸载说明、支持矩阵、原始评估记录及已知限制。自动模式按 2026-09-30 用户决定改为可开启的后续扩展，默认关闭。

运行记录必须包含要求版本、代码快照、测试计划、运行环境和证据引用。演示视频可辅助说明，不能替代原始证据。

## 3. 发布门槛

- 当前首版范围的案例均有实际运行记录和预期一致的结果；A23、A27、A29 及 A26 的自动部分仅在发布自动模式时必需。未发布的扩展注明不在此次范围，不计为通过。
- 真实宿主主动接入未完成时，只能交付并标记为 Core/CLI/MCP 原型，不能称首版完整交付。没有自动模式不阻挡主动模式首版，但不得宣传自动接入。
- 至少一个正确案例、一个真实缺陷案例、一个环境缺口案例在同一构建上演示。
- 149 元缺陷修复后必须产生新运行并通过相同含义的检查，不能降低预期。
- 无真实模型凭据时，模拟测试可证明工程接口，但需求理解与动态规划阶段未验收。
- 检查超时后不能遗留持续占用端口的被测进程或容器；清理失败要可见并提供可执行恢复说明。
- 敏感字段、路径限制、原话引用核对、错误通过防线属于硬门槛。

这组门槛证明指定首版范围得到验证，不代表对任意任务的可靠性保证。

## 4. 怎样证明比“Agent 说完成”更有用

### 三组对照

使用相同任务对话、相同交付快照和相同测试环境：

| 组 | 方法 | 目的 |
| --- | --- | --- |
| A：声明基线 | 仅按交付声明是否声称完成判断 | 衡量只相信自报会漏掉什么 |
| B：固定测试基线 | 运行冻结的项目现有测试/构建，读取结果 | 衡量普通测试执行已经解决什么 |
| C：VibeGuard | 从对话整理当前要求，生成并运行独立检查，保存逐项证据 | 衡量需求级验收新增什么价值 |

A 组尽量使用真实记录的 Agent 声明。人工构造的声明必须标记为合成案例，不能据此宣传某个模型真实说谎。三组接收相同交付物，不能给 VibeGuard 额外答案或更容易的项目。

各组使用独立复位的应用与测试数据，固定依赖、时间条件和资源预算，避免前一组已经用掉优惠券、改了数据库而影响后一组。运行顺序交替；相同项目的多个版本按同一任务分组统计。

### 样本规模

先用 12 个独立任务做最小工程评估：优惠券 4 个、登录/权限 4 个、表单/列表操作 4 个，包含中文补充、改口、取消和多轮任务。每个任务保留正确版、带已知缺陷版、无法运行版，共 36 个交付。

首次竞赛前若预算允许扩展到 20 个任务 × 4 种交付，加入“现有测试全绿但漏需求”的交付，共 80 个。任务是统计分组单位，不能把同一项目的几十个断言冒充几十个独立任务。

至少三分之一任务在提示词、阈值和规则确定后保留为隐藏评估集。用于调提示的任务不再算隐藏评估。选择一部分任务重复运行 3 次，观察随机波动、额外成本和不稳定结果。

### 标准答案

两个成员分别标记：当前有效要求、已知缺陷、允许的结论和环境缺口，再讨论分歧。最终答案与隐藏检查由评估程序持有，不提供给 Planner 或被测 Agent。

缺陷确认需要真实复现。环境不能启动通常对应无法验证；不要把所有无法验证当成成功发现 Bug。多种实现都满足要求时，不因与某一份参考实现不同而判错。

### 报告指标

| 指标 | 定义 |
| --- | --- |
| 错误放行 | 已知存在必需需求缺陷，却报告该范围全部 VERIFIED；同时报告数量/缺陷交付总数 |
| 缺陷发现 | 已知缺陷被正确判 FAILED 并有有效证据；UNVERIFIABLE 不算发现 |
| 正确交付误报 | 正确交付被判 FAILED 的数量及原因 |
| 无法验证 | 输出未知的数量，按材料、环境、预算、规划失败分别统计 |
| 需求遗漏 | 人工有效要求中未被覆盖且未明确说明缺口的数量 |
| 原话与证据有效性 | 引用是否逐字一致、附件是否真实存在、记录是否属于当前运行和条件 |
| 成本与耗时 | 每任务输入/输出 token、调用次数、补救费用、工具时间、端到端中位数与 P95 |

小样本以原始数量、案例和限制为主。没有统计依据不宣称显著优于、百分之百可靠或推广到所有 Agent。

## 5. 主模型怎么选

选 2～3 个候选 API 模型，固定同一对话、材料、工具、预算与输出契约，比较有效要求提取、引用准确性、检查设计和完整运行成本。先淘汰关键遗漏或错误放行严重的候选，再看费用与速度。

若模型费用只便宜但补救调用增加，应按任务总费用比较。记录供应商、模型版本、提示版本、日期和配置。不要让模型选择过程拖延 M1 的确定性证据闭环。

## 6. Jev / Laya 的独立优化实验

只选一个具体高频问题，例如日志片段相关性或候选验证工具排序。对照规则、主模型原流程、Jev、Laya；本地模型计入加载时间、内存与维护成本。旁路阶段不影响正式结论。

可以启用的条件：在保留的任务集上降低完整任务费用或耗时，未增加已观察到的关键遗漏和错误放行，且异常时可回退。不得仅因单次判断便宜、返回概率很高或项目热度高而启用。

有限样本里没发现退化不等于证明永不退化；保留关闭开关，新增失败案例进入回归集。两者都不是首版发布门槛。

## 7. 比赛演示顺序

1. 展示用户原始要求与中途将 100 改为 150 的消息。
2. 展示干活 Agent 的交付声明和现有测试通过记录。
3. 用户说“用 VibeGuard 验收”，现场取得 150/149 的真实对照结果；自动触发留作用户开启后的扩展演示。
4. 展开 149 元失败证据，说明为什么整体门槛未完成。
5. 修复后对新代码快照复验，保留前后两份报告。
6. 演示一次环境缺口或中止，诚实输出无法验证。
7. 展示对照评估的实际数量、花费和已知限制。

尽量让评委看到“用户要求的哪句话没有落实”以及“证据怎样证明”，技术组件只在需要解释时出现。
