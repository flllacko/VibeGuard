# 在原聊天中纠正和确认要求

更新：2026-10-18。要求审查已接入模型解释自然表达；外部项目隔离运行、浏览器和数据库验收仍未接入。

## 用户怎样使用

1. 在已接入的平台说“用 VibeGuard 验收”。长任务先确认本次阶段；已经确认过的范围继续沿用。
2. VibeGuard 展示要求清单：稳定编号 R1/R2、用户原话、当前理解、本次排除的条目和需要澄清的 Q 编号。
3. 用户在原聊天按自己的说法纠正，例如：

   - “退款恢复那块这次先放下，另外两项按你理解的查。”
   - “门槛还是按一百二十吧，减免换成十五。”
   - “密码登录换成短信验证码，登录后回到刚才的页面。”

   也可以使用编号表达，但不强制用户学习命令：

   - `第2条改成每个用户只能领取一次`
   - `取消第3条`、`第3条本次不验`
   - `新增：错误密码返回401`
   - `合并R1和R2`
   - `Q1作为背景`、`Q1作为要求：接入后读取当前聊天历史`

4. 修改后展示差异和新清单。用户回复 `理解正确，开始验收` 或 `确认`。
5. 保存确认后的要求版本。此时没有执行记录的条目仍为“无法验证”；不会把用户确认当成通过证据。

已确认清单还可以继续修订；新版本需要重新确认，旧版本不能继续作为当前规划输入。编号不因删除而重排，原话和修改依据都保留。

### 怎样理解用户的纠正

最初版本只有固定句式解析，不能作为最终交互。现在正式 CLI/MCP 默认给修订流程注入模型解释器，复用已配置的供应商和模型（默认 DeepSeek Flash），无需额外 API 配置。

模型将自然回复转换成通用操作：修改、排除、恢复、补充、合并和澄清。程序验证原话引用、修改对象、原文分段去向和当前版本，保留来源后展示新版。不会为“退款”“验证码”等每个业务或每种说法添加一条源代码规则。

语义理解仍可能出错。对象不明确时应提出具体问题；来源、对象或覆盖校验失败时整份修改不应用。不能把这些程序检查称为语义正确率。用户同时修改和表示同意时，仍先展示新版再确认。

单独的明确“确认”等整句回复不用额外模型调用。其他表达通常只解释一次，模型只接收当前要求、待定问题和这次用户回复，不重复发送完整历史；原件仍在本地保留。修改候选、模型标识和用量保存，读取及相同回复重试不重新调用模型。网络或输出失败不会无限自动重试。

旧固定解析器保留用于历史记录重放及未注入模型的开发调用。正式入口已经接模型，不能以旧解析器的夹具结果宣称真实模型准确。

## Agent 与 MCP 怎样配合

继续使用原有三个工具，不增加一个新的安装入口。

1. `verify_task` 的外部任务整理结果附带 `requirementReview`，新清单提示用户可按自己的说法纠正。
2. Agent 必须将 `requirementReview.text` 作为完整独立消息原样展示，不能在清单后另附改写要求的说明。完整展示内容包含短标识和回复提示，不需要用户手输 UUID。
3. 用户真实回复后，再调用：

   ```json
   { "requirementReview": { "reviewRef": "工具返回的编号" } }
   ```

4. 采集 Hook 即使看到旧 `taskRef` 也重新采集当前聊天。服务读取新原始用户消息，不读取工具参数里的“用户意思”。
5. 查询 `get_verification`，展示修订后的清单或确认状态。

`taskSelection` 与 `requirementReview` 不能同时提交；范围选择和要求修订分步进行。工具不接受 `confirmed`、`verdict` 或由干活 Agent 直接提交的修改内容。

运行中的 MCP 服务需要重载才能取得新参数和描述。采集 Hook 启动的是本机构建产物；本轮没有更改全局 MCP 配置或钩子配置。真实平台中的完整真人修订流程尚待重载后实测。

### 更新后仍读不到新清单时

如果工具报“只接受 original-user-review-v1”或“不识别 interpretation”，先检查当前连接是否仍在运行旧版本。重新构建不会替换已经载入内存的 MCP 代码；无需为此重新运行接入向导或改 API Key。

在平台 MCP 设置中重启或重新连接 VibeGuard；如果没有重载入口，完整退出平台后重新打开原聊天。Codex 官方的[连接说明](https://learn.chatgpt.com/docs/extend/mcp?surface=app)包含保存后 Restart 的步骤；不同版本的具体界面可能不同。随后使用**原聊天当前连接的** `get_verification` 读回新版记录，确认不再报旧格式错误。独立启动的 doctor 或测试 MCP 只证明新进程可用，不能证明宿主连接已经更新。

范围候选和要求清单仍须来自真实原文。2026-10-18 的真人测试准备只在本地保存新短任务的范围候选，尚待用户选择；没有为省略确认而把裁剪材料标成完整宿主历史，也没有将旧长历史送入模型。

## 保存与核对

- 初始清单绑定任务、原文摘要、范围和要求整理记录。
- 每次回复绑定相同宿主和会话、完整旧前缀、最新独立展示的完整清单，以及唯一新增的原始用户回复。
- 拒绝其他聊天、原文改写、缺页、确认附件未知、夹入多条新用户消息以及旧清单被不同回复重复消费。
- 每版独立保存；同一回复重试复用结果。重启读取会核对原件并重放修订关系。
- 图片、缺消息、整理失败等缺口不能通过“确认”清除。已读文字的歧义可通过明确 Q 分类解决，但不修改原始整理记录。
- 本地哈希和重放用于发现不一致，不构成对同权限攻击者的防篡改保证。

`confirmedRequirementSnapshot` 只提供后续规划所需的已确认要求，不执行任何检查。不提供新的当前聊天快照时，导出内容明确标记为历史版本；规划前必须重新核对当前材料。后续执行还需要绑定具体交付快照。

## 开发调试入口

普通用户优先使用原聊天。下列命令用于开发和排查：

```powershell
# 查看已经生成的审查清单；不会调用模型
node dist/cli.js requirement-review REVIEW_REF

# 回复内容从新采集原件读取，命令参数本身不能确认
node dist/cli.js verify-task FRESH_TASK_REF --review REVIEW_REF

# 导出已确认历史版本；不是执行证据
node dist/cli.js confirmed-requirements REVIEW_REF

# 同时核对新登记的当前聊天快照
node dist/cli.js confirmed-requirements REVIEW_REF --current-task FRESH_TASK_REF
```
