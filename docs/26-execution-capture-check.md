后续更新（2026-10-21）：外部 MCP 入口已接一次性采集凭据，独立产品命令“用 VibeGuard 验收”可作为非业务请求保留；其他未审查用户消息仍阻断。原生宿主自动触发仍待实测，见[宿主接入增量](27-host-external-mcp-bridge.md)。下文保留本阶段当时的规则和实测。

## 改了什么，为什么

此前准备项目时已经核对要求版本，但以后只用计划编号就能启动。若新用户消息已经采集、尚未登记成要求修订，旧计划本身仍然合法，执行入口需要再次核对材料。

现在新执行必须显式传入本次采集编号：

```powershell
node dist/cli.js project-run PLAN_REF --current-task TASK_REF --data-dir DATA_DIR
```

`TASK_REF` 是接入层独立采集并登记的原始对话编号，不是 Agent 写的任务摘要，也不是手填“确认通过”。缺少参数不会自动回退到准备项目时的快照。Core 和 CLI 使用同一个检查，没有通过省略参数关闭检查的模式。

## 执行时发生什么

1. 读取计划绑定的要求版本和固定交付。
2. 复用已有要求当前性检查：同一宿主/会话、原始前缀一致、独立采集、材料完整性及附件账目未变化。
3. 存在确认之后的新用户消息就先拒绝，等待审查。这里不自动判断“只是聊天”或“肯定改了业务”，也不把普通验收请求当作新的业务规则。
4. 材料一致才创建运行记录并启动容器；正式 HTTP 检查前后再次核对同一快照和要求版本。
5. 报告保存采集编号、原文摘要、会话、要求版本和核对时间。历史读取检查保存的源材料，不要求旧版本仍是最新要求。

只有助手交付提示等追加、没有新增用户内容，且其余检查都满足时，可以继续执行。若审查后要求确实改变，仍按前一阶段重新确认、准备和规划；不能把快照参数当作忽略改口的开关。

新增模块 `src/execution-capture.ts`；调用与保存接入 `external-runner.ts`、`cli.ts`。开发评估入口同步显式传入其预置采集；它们不是自动采集真实平台的实现。

## 当前边界

**这能核对提交的快照，不能证明提交方一定拿来了平台实时最新历史。** 如果调用方显式选择一份更旧但仍符合规则的快照，现阶段没有平台侧时点证明可识别它。时间戳或参数名称不能填补这个缺口。

运行中重新检查的是同一份材料与要求版本，不是持续轮询平台所有新消息。新增用户消息一律先保守拦截，尚未在此入口区分普通验收请求和业务改口。

未修改平台全局配置，没有真实宿主主动调用或自动采集最新时点的实测；MCP 工具、桌面、安装包、新平台及其他运行工具未扩展，仍限当前 Node HTTP 范围。

下一最小动作：由宿主接入在主动验收时独立采集并传入当前会话快照，打通这项检查与真实入口，同时处理“验收请求本身是新消息”的审查流程；不能让干活 Agent 自选旧快照来证明当前完成。
