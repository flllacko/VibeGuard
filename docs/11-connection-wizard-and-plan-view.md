# 接入向导与可读验收清单

更新：2026-10-14。当前交付是源码原型中的统一向导，不是已发布的安装包。

## 用户现在怎样使用

准备好 Node.js 24，在源码目录完成 `pnpm install`、`pnpm build` 后，Windows 可双击根目录的 **connect.cmd**，或者运行：

```powershell
node dist/cli.js connect
```

按提示选择 Codex 或 Claude Code，查看将修改的文件、对话读取行为、密钥引用和授权说明。输入 `y` 才会安装连接配置。明确平台时可直接运行 `connect codex` 或 `connect claude-code`。

向导会把 MCP 与对话采集钩子一起处理。用户无需分别拼接配置，不用把密钥发到聊天。自动收尾验收仍关闭，平时由用户主动说“用 VibeGuard 验收”。安装权限、验收范围和最终接受交付是不同的决定。

| 环节 | 当前实现 |
| --- | --- |
| 选择平台 | 同一向导，提供 Codex、Claude Code 两个配置适配器 |
| 展示改动 | 显示目标文件、用途、摘要；不输出旧配置正文或密钥值 |
| 安装连接 | 用户确认后合并 MCP 和采集钩子；保留其他服务、钩子和权限设置 |
| 工具自检 | 独立 MCP 客户端启动本包并读取三个工具；不调用模型 |
| 平台信任、重载 | 需要用户按平台提示完成；向导不写信任状态 |
| 当前会话、项目与证据检查 | 明确显示待验证，需要真实平台链路核对 |
| 已发布安装包、其他平台自动配置 | 尚未提供；其他平台不能照搬这两个适配器 |

只是重新查看配置，不想写入时：

```powershell
node dist/cli.js connect codex --dry-run
node dist/cli.js doctor codex
```

原来的 `setup codex|claude-code` 仍只生成手动填写说明。不具备交互终端时，`connect` 默认也只预览；`--yes` 是明确应用配置的选项，不能因为 Agent 能执行命令就视为用户已授权修改平台。

## 写入哪些位置，怎样保留已有内容

| 平台 | 当前用户级目标位置 |
| --- | --- |
| Codex | `~/.codex/config.toml`、`~/.codex/hooks.json`；设置了 `CODEX_HOME` 时使用该目录 |
| Claude Code | `~/.claude.json` 的用户级 MCP、`~/.claude/settings.json` 的钩子；支持其配置目录变量 |

Codex 的 MCP 与钩子配置位置及非受管钩子的信任要求已按 [OpenAI MCP 文档](https://learn.chatgpt.com/docs/extend/mcp)、[OpenAI Hooks 文档](https://learn.chatgpt.com/docs/hooks)核对。Claude 的用户级服务与设置参考 [官方 MCP 文档](https://code.claude.com/docs/en/mcp)和 [Hooks 文档](https://code.claude.com/docs/en/hooks)。**配置合并测试通过，不代表 Claude 应用内接入已实测。**

Codex TOML 使用锁定的 smol-toml 1.9.1 解析，仅追加或替换 VibeGuard 表，再核对整份配置解析结果是否只发生预期变化。其他配置原文尽量保留；内联表等无法安全处理的形式会停止，提示手动接入，不重写整份文件。JSON 配置保留其他属性，文件格式会重新排版；无效 JSON 不覆盖。

重复安装不会重复添加同一采集钩子。不同路径的旧 VibeGuard 采集器会报告冲突，避免两个采集器同时运行。已经禁用的钩子和工具权限不自动开启。符号链接、junction、超大或无法解析的配置不自动修改。

写入前重新核对配置是否在预览后变化；临时文件准备好后再逐个替换，失败时尝试恢复本轮已改内容，不创建持久备份。多个文件之间不是文件系统的原子事务，不能承诺抵抗同权限并发恶意修改；恢复失败会明确报告部分安装。

## 怎样理解自检结果

自检分 `passed`、`pending`、`failed`，不会只给一个容易误解的“全部接好了”：

- **配置通过**：连接配置与当前向导一致；平台可能还没有加载。
- **工具连接通过**：独立客户端确实读到三个 MCP 工具；平台自己的进程是否连接仍需确认。
- **模型凭据可读**：当前进程能读到变量；没有请求 API，不证明密钥有效或平台正确转发。
- **当前对话采集待确认**：回到平台信任、重载后，检查真实采集收据和消息；换另一条聊天验证没有串线。
- **项目读取待确认**：需要选择本次任务的项目与读取范围。
- **证据保存与读回待确认**：需要实际验收运行，读取属于该运行的证据。

Codex 在运行非受管钩子前要求审查并信任当前定义，CLI 官方入口为 `/hooks`；桌面应用按钩子管理入口和提示操作。信任后再重载连接并实测。采集成功后改写此次工具输入需返回 `allow`，只涉及这一条验收工具调用；此影响在安装前展示。向导不设置跳过钩子信任的启动参数。

## 用户怎样查看“准备验什么”

已有冻结计划时：

```powershell
node dist/cli.js plan-record <计划摘要>
```

默认展示可读清单；`--format json` 保留原始开发者数据。每条当前要求都有：

1. 用户原话及整理后的要求。
2. 怎样才算做到。
3. 准备使用哪些检查和预期。
4. 哪些是为取得证据补充的检查。
5. 暂时没有检查或只能检查部分的具体原因。

例如：

> 用户原话：“SKILL.md 必须在文件夹第一层，”
>
> 怎样算做到：技能文件夹根目录中存在 SKILL.md，类型为文件。
>
> 执行：检查已授权的实际位置。

“确认理解”不等于给交付点通过，也不证明计划没有漏项。当前不增加每次都要用户签字的审批门禁；语义规划质量仍需开发者评估和补充自动规则。出现含糊要求时，现有整理门禁继续保留缺口。

MCP 的 `get_verification(includeReport: true)` 对已绑定计划的执行报告另附 `acceptancePlan`。其中保留原话、标准、步骤与缺口，不含 `approved` 或 `verdict`。它是计划定义，可与实际报告一起审视；默认查询不重复返回详细计划，减少上下文。
