# VibeGuard 最终体验：原 Agent 内验收，本地保留证据

日期：2026-10-19。以下是结合客户目标与公开资料提出的产品方案；设计目标不是已完成能力。当前实现见[实施状态](implementation-status.md)。

## 一句话

用户照常让 Agent 干活，说一句“用 VibeGuard 验收”，就能看到哪些原始要求已做到、哪些失败、哪些证据不足，并展开真实记录。

适合当前项目的组合：**Agent 内入口 + 独立本地验收引擎 + 轻量桌面验收台**。`.exe` 是 Windows 安装和辅助界面的交付方式；用户日常不应为每次验收打开另一个应用、找聊天、复制材料或填写编号。

## 为什么选择这个组合

| 形态 | 适用情况 | 对本项目的判断 |
| --- | --- | --- |
| 只提供命令行 | 开发、调试、CI | 保留，但普通用户不应依赖命令和源码 |
| 只提供插件或 MCP | 原聊天触发最自然 | 可简化入口，但完整原文采集、运行环境和证据保存仍需实现 |
| 只提供独立桌面 App | 接入指导、大量证据、历史查阅 | 每次跳出原聊天会多一步，适合作为辅助入口 |
| 三者共用同一引擎 | 安装后原聊天验收，必要时展开详情 | 推荐路线；不维护三套判定规则 |

这是对“方便接入、原聊天使用、真实执行”的工程取舍，不宣称存在对所有用户都最优的外形。没有必要因为安装器叫 `.exe` 就改写已实现的 TypeScript Core，也不因 Electron 或其他外壳更新就重做验收规则。

## 普通用户的完整体验

### 第一次

1. Windows 用户下载签名安装包，安装必要引擎与轻量界面，不需要另外装 Node、pnpm 或下载源码。
2. 选择使用的平台，向导展示读取范围及需要的平台信任步骤；支持插件安装的平台优先引导原生安装，其余生成或合并必要配置。
3. 分别自检：工具可调用、当前会话身份正确、任务原文及材料够用、交付可访问、执行环境就绪。不要把“已连接 MCP”当作全部成功。
4. 项目运行方式尽量从标准配置识别；不确定的启动方式、测试账户或接口契约由用户确认一次并保存。不能为了省一步擅自运行未知命令。
5. Docker 仅在需要动态运行项目时检查；缺少时给出具体操作。安装 VibeGuard 不等于已经安装或授权 Docker。

这些是发行目标，安装包、自动发现和全部平台向导尚未交付。平台要求的信任与重载无法保证省略，不能宣传“任何 Agent 零步骤接入”。

### 每次短任务

用户在原平台提出任务，Agent 交付后，用户说“用 VibeGuard 验收”。接入层依据宿主提供的当前会话身份取得原文与交付，调用独立引擎。清楚且已在授权范围内的任务以直接执行为体验目标；出现歧义时展示简短的原话与范围供用户纠正，不让用户编写测试脚本。

原聊天显示三态数量及逐项摘要，每项包含“用户原话 → 怎样算做到 → 实际观察 → 结论 → 证据入口”。详细日志保存在本地，默认不塞进模型上下文。支持交互卡片的平台在聊天内展开；其他平台使用文字与本地报告后备入口。

### 长任务

用户可说“验收刚交付的这一阶段”。系统保存完整原始历史与版本关系，只把相关且当前有效的要求送入规划；取消的要求、未来阶段、背景讨论和操作授权分别记录。边界不清时让用户确认范围，不能拿全聊天出现过的每句话都要求本阶段完成。

修复后创建新交付与新证据，保留旧报告；未变化的项目设置复用，旧结论不自动继承为新版本已通过。当前已实现确认要求门禁，简化正常任务确认次数属于后续体验优化，不能提前绕过现有来源与版本检查。

### 用户打开桌面时

首屏围绕“待验收任务、正在运行、需要用户处理、最近结果”，并可按来源平台筛选。重点页面是连接自检、范围/要求纠正、执行进度、证据展开、历史对比。单条卡片可回到原 Agent 会话；回跳能力按平台实测。

运行进程由宿主或本地启动器按需拉起，界面关闭不应使证据消失；已开始验收的后台任务需明确展示存活/取消规则。后台常驻不是强制前提，也不注册隐蔽系统服务。此生命周期尚待桌面阶段实测。

## 各组件职责

- **插件/Skill**：告诉宿主怎样发起与展示验收，打包必要接入项；不是判定者。
- **MCP**：通用的工具调用接口，传登记引用、查进度、取结果；不是聊天历史授权协议。
- **平台采集器**：依据当前会话身份取得原始材料与记录，注明分页、附件、截断、缺页；优先公开接口/导出，其次可核对版本的本地格式。
- **Hook**：在明确节点触发采集或已开启的自动验收。自动模式默认关闭，并按任务/交付去重，避免验收调用再次触发验收。
- **Core 与独立运行器**：整理版本、拆标准、规划取证、运行检查、保存证据、按规则汇总结论。干活 Agent 只能申请，不能上传一个“通过”替代观察。
- **桌面验收台**：安装、接入修复、复杂人工审查、证据和历史。单个平台入口失效不应让本地报告失效。

原始对话本地保留。首次使用明确说明云端模型会收到哪些任务材料；规划阶段只发送已审查的有效要求和必要接口信息。用户没有授权的聊天、其他项目及凭据不因“已安装”而自动进入模型输入。

## 什么值得借鉴

2026-10-19 只读核查，下面是文档证据与工程推论，不是本产品适配已实测：

- [Claude 插件](https://code.claude.com/docs/en/plugins)把 Skill、MCP、Hook 打包为一个安装单元；[Hook 文档](https://code.claude.com/docs/en/hooks)提供会话身份与 transcript_path。值得借鉴接入包装，不等于日志永远完整。
- [Codex 插件](https://developers.openai.com/plugins/build/plugins)支持组合能力，但带 Hook 的手动桌面安装与信任有单独要求，不能假定商店安装即自动可信。
- [Cursor](https://prod.cursor.com/help/customization/mcp)提供 MCP 安装入口及部分聊天内 UI；[Qoder](https://docs.qoder.com/user-guide/chat/model-context-protocol)也提供 MCP 设置。入口包装按平台选择，Core 复用。
- [MCP 架构规范](https://modelcontextprotocol.io/specification/2025-11-25/architecture)明确完整聊天保留在宿主，服务仅获得必要上下文。所以采集问题不能靠统一 MCP 配置自动解决。
- [iFixAi](https://github.com/ifixai-ai/iFixAi)使用共用引擎的 CLI/向导/插件入口，值得借鉴安装与触发体验；它的诊断套件和评分不直接替代本任务原话对应的实际验收证据。
- [Agent Sessions](https://github.com/jazzyalex/agent-sessions/blob/main/README.md)展示了本地多来源历史浏览的形式与按来源区分能力的做法。会话可浏览不等于任务已验收，也不能直接把其 macOS 应用称为 Windows 可用方案。

Qoder、WorkBuddy、豆包、ZCode、Trae 等继续保留为接入目标，按实际开放能力与真实测试纳入支持矩阵。不能把品牌名单写成已支持名单。

## 怎样知道真的方便、高效

发行验收记录：首次接入需要的人工操作、成功后每次验收的配置次数、手动导出次数、澄清次数、执行耗时、输入输出 token 与实际成本。目标是正常验收无需复制聊天或填写内部编号。

原文和原始证据本地存储；模型接收必要片段；同一版本的计划可读回，不再为展示重复调用模型。跨运行复用与缓存必须绑定要求、模型/提示、配置和交付版本，并单独验证，不能以省 token 为由漏掉条件。

同时记录缺陷误放行、错误失败、要求遗漏和无法验证原因。点击少而结论不实不算产品完成；独立进程和哈希也不能被宣传成同权限攻击下绝对防伪。
