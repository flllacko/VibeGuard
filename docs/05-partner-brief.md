# VibeGuard：简明介绍

## 我们想解决什么

AI 写完代码常说“完成了、测试通过”，但用户不知道它有没有漏需求、有没有真的运行，也不知道修好一处后是否破坏了其他功能。

我们做一个独立验收助手：**Agent 负责做，VibeGuard 负责检查，人决定是否接受。**

第一版从代码任务开始，长期可以扩展到能客观检查的网页操作、数据处理等任务。

## 用户用起来是什么样

用户继续在原来的编程 Agent 里说需求。第一版默认由用户说“用 VibeGuard 验收这次任务”，通过 MCP 调用独立验收程序。长任务可以阶段验收，最后再验收全部有效要求。自动验收以后作为用户可开启的模式，默认关闭。

例如：

> 用户：增加优惠券，满 100 元减 20，每张券只能用一次。
>
> 用户后来补充：门槛改成 150 元，其他不变。
>
> Agent：已完成，测试通过。
>
> 用户：用 VibeGuard 验收这次任务。
>
> VibeGuard：按照你的原话“门槛改成 150 元，其他不变”实际检查：
>
> ✅ 150 元订单优惠 20 元，应付 130 元。
>
> ❌ 149 元订单也优惠了 20 元，实际应付 129 元，预期应付 149 元。
>
> 展开证据：能看到请求、响应、订单记录和对应代码版本。

这是模拟产品效果。真正实现后，报告必须来自实际执行。修复以后会重新验收，并保留前后两份记录。

## 产品最重要的三件事

1. **记清用户到底要什么。**读取完整任务对话，保留原话，整理后来的修改、取消和当前有效要求。
2. **实际去验证。**运行项目、调用接口、操作页面、查看测试数据，既检查正常情况，也做必要的反例和边界检查。
3. **把事实说清楚。**每项显示“原话 + 已验证/失败/无法验证 + 证据”，没有证据不装作通过。

我们要检查用户任务的完成情况。即使项目原有测试全部通过，漏掉的需求仍然要指出。验收器推导出的额外建议会单独标明，不冒充用户原先的要求。

## 大概怎么做

采用 TypeScript + Node.js。用一个模型整理要求和设计检查，Pi 帮忙调用模型与工具；程序执行检查并保存证据，Playwright 操作浏览器，SQLite 和文件保存历史记录。

钩子负责在合适节点自动启动；CLI 方便调试；MCP 让不同 Agent 主动验收或读取报告。它们共用一个验收核心。先接通一个真实平台，再逐步扩展。

Jev、Laya 只作为以后可能省钱或加速的优化实验。第一版不依赖它们，也不靠模型的“通过概率”决定完成。

## 两个人怎么分工

- 一个人偏“怎样验收”：整理要求、拆验收目标、判断风险、设计报告和评估案例。
- 一个人偏“怎样拿证据”：运行项目、接口与浏览器工具、存储记录、钩子和 MCP 接入。

先一起做通一个优惠券例子，再分工。第一版重点交付：可用的验收核心、命令行、MCP、一个真实平台的主动验收接入和一份能展开证据的报告。自动验收单独作为扩展功能验收。

## 怎样证明有用

拿同一批正确和有缺陷的交付，比较“只信 Agent”“只跑原有测试”和 VibeGuard，记录漏掉了哪些问题、有没有误报、花多少钱和多久。

我们不承诺发现所有 Bug，也不承诺本地记录绝对无法伪造。我们要先做到：**用户能看清自己哪句话得到了验证，哪句话没有完成，以及凭什么这么判断。**
