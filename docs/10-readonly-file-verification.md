# 只读文件验收：操作与真实案例

日期：2026-10-04。当前为开发原型；已接入 Core、CLI 和同一套三个 MCP 工具。

## 1. 本次做出了什么

原先能从真实聊天整理要求，但对真实文件交付缺少执行证据。现在的链路是：

完整任务原文 → 当前有效要求 → 模型生成文件验收计划 → 程序检查覆盖与读取范围 → 独立进程读取文件 → 保存原始清单和检查记录 → 原聊天按“原话＋结果＋证据”展示。

没有为技能安装写专用验收脚本。执行器只提供两种操作：

| 操作 | 能证明什么 |
| --- | --- |
| `entry_exists` | 指定相对位置存在预期的文件或目录 |
| `tree_compare` / `structure` | 完整相对路径、文件与目录类型相同，包含空目录 |
| `tree_compare` / `content` | 上述结构相同，且逐文件 SHA-256 相同 |

模型选择操作和预期，程序独立观察并判断。目录存在不能证明目录内容完整，也不能证明技能加载或应用可运行。

## 2. 项目配置怎么写

创建 `file-profile.json`，把以下两个绝对路径换成实际参考源与交付位置：

```json
{
  "schemaVersion": 1,
  "profileId": "my-file-delivery",
  "description": "核对本项目的文件交付",
  "roots": [
    {
      "rootId": "original",
      "role": "reference",
      "description": "交付前的原始文件夹本身，非父目录",
      "path": "C:/VibeGuardCase/original"
    },
    {
      "rootId": "delivered",
      "role": "delivery",
      "description": "要求交付的目标文件夹本身，非父目录",
      "path": "C:/VibeGuardCase/delivered"
    }
  ]
}
```

`rootId` 是计划使用的别名，`path` 是这次允许检查的位置；这些配置由用户或可信接入程序登记。根本身的相对路径是空字符串 `""`；第一层文件是 `"SKILL.md"`，不要再拼一次根文件夹名称。允许根本身是单个文件。全部根都会被读取，**只配置本次必要的目录**。

配置不包含“本次要查 SKILL.md”等任务标准。下次同一目录的任务变了，应从新对话生成新要求和计划；执行器源码无需增加专用脚本。完整复制或内容保留需要参考源；没有参考源时仍可查位置，但内容对照不能通过。

默认限制：合计 5,000 个条目、单文件 32 MiB、合计 128 MiB、深度 32。需要时在 `limits` 中指定 `maxEntries`、`maxFileBytes`、`maxTotalBytes`、`maxDepth`；超限会说明无法验证，不截断后宣布通过。

## 3. 实际怎么调用

当前须在仓库构建后运行。先取得完整任务 JSON 和已完成的要求整理；已有整理时直接复用 ID，避免重复消耗模型：

```powershell
pnpm build
node dist/cli.js resolve --task task.json --provider deepseek
```

把输出的要求整理 ID、计划摘要和 taskRef 依次填入：

```powershell
node dist/cli.js file-plan --resolution <要求整理ID> --profile file-profile.json
# 先看计划：每条要求的范围和相对路径是否正确
node dist/cli.js plan-record <计划摘要> --format json
node dist/cli.js register-task --task task.json --file-plan <计划摘要> --file-profile file-profile.json
node dist/cli.js verify-task <taskRef>
node dist/cli.js verification <runId>
```

默认 DeepSeek Flash，读取已配置的 `DEEPSEEK_API_KEY`；自选模型才加 `--model`。`file-plan` 只生成并冻结计划，不代表验收通过。计划格式、要求覆盖、来源绑定或读取范围不合法时，不会执行该计划。

文件计划登记后，在已连接并重载的 MCP 中，用户可说：

> 用 VibeGuard 验收 taskRef 为“登记得到的编号”的任务。查完逐条展示用户原话、实际结果、证据；无法验证的说明缺什么。

Agent 调 `verify_task({taskRef})` → 用返回的 runId 查询 `get_verification` → 需要原始记录时调用 `read_evidence`。工具不能提交脚本、任意路径或通过结论。相同入口适用于支持该 MCP 服务的平台；完整聊天的获取仍需要各平台采集或用户导入。

当前还没有“当前聊天自动选择范围、自动生成并绑定文件计划”的一键流程。文件执行不需要 Docker，因为不执行项目代码；后续运行代码仍需隔离能力。更新并构建源码后，要重载宿主正在运行的 MCP，已有进程不会自动更新。

## 5. 实测中暴露的问题与局限

这次用已知任务反复修改提示词，是开发复测，**不是独立保留样本评估**：

1. 第一份候选误把“安装到目录”扩写成宿主加载，还把内容检查绑到纯结构要求；人工审查发现后未执行。
2. 第二次返回空 checks 的标准，被程序格式检查拒绝。
3. 第三份候选多拼一层文件夹名；人工审查发现后未执行。
4. 明确要求范围、空标准规则及根目录含义后，第四份候选审查通过并执行。

结构门禁不能自动识别全部语义错误。当前仍需审查冻结计划；下一批不同文件任务应在不调提示词的前提下评估误报、漏项和成本。

执行器读前读后核对文件内容和元数据。稳定的缺文件、错误类型或内容差异是失败；参考源缺失、读取失败、超限、符号链接/junction、特殊文件，或读取期间发生变化，是无法验证。证据目录必须位于被检查根之外；清单含路径、类型、大小、内容哈希，不保存文件正文，也不把清单发给规划模型。

本轮未给文件系统加锁，不能承诺抵抗同权限进程刻意修改；本地哈希也不能防止证据与清单被同时重写。文件证据不能证明宿主加载、应用运行、安全性或历史交付状态。

## 6. 如何确认实现正确

`pnpm build` 与全套 53 项测试通过。新增测试实际构造并检查：同大小但内容不同、缺空目录、多文件、缺源与缺目标、错误文件类型、读取限制、junction、读前读后变化、路径越界与自比、MCP 重启读回、交付改变后新运行以及证据改变后拒绝读取。缺陷只在独立临时测试目录构造，没有修改真实技能交付。
