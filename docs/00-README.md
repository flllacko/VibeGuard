## 2. 已确认的约定

- 产品名称暂定 VibeGuard，两人比赛项目；长期面向可验证数字任务，第一版从 AI Coding 开始。
- 接受完整任务对话，整理当前有效要求，再拆解验收目标。
- 拆解顺序为“原话 → 当前有效要求 → 可验收标准 → 项目执行步骤 → 原始证据 → 结论”；缺口要指出发生在哪一层。
- 报告核心是“用户原话 + 验证结果 + 实际证据”，保留后续修改、取消的关系。
- 干活 Agent 的完成声明不能决定验收通过。没有实际执行记录不能标已验证；存在其他明显解释时补充对照检查，否则无法验证。
- 用户继续在原 Agent 工作流程中使用，默认主动发起验收；长任务可阶段验收和最终验收。自动验收作为用户可开启的扩展模式，默认关闭。
- 第一版采用 TypeScript + Node.js；Pi 负责底层模型与工具循环，VibeGuard 控制验收流程与证据规则。
- Core + CLI + MCP + 首个宿主接入；使用成熟模型 API。Playwright 用于浏览器检查，SQLite 和文件用于本地证据存储。
- Jev、Laya 只是可选优化实验，不是第一版依赖，不控制最终通过结论。
- 第一版不做大型 Web 平台、大型多智能体、本地大模型部署或微调；不做无限自动修复。

## 3. 本文补充的工程默认值

以下是乙方提出的可调整默认值，不冒充客户已经逐项指定的要求。

| 项目 | 默认方案 | 调整条件 |
| --- | --- | --- |
| Node 版本 | 24 LTS，开始实现时核查支持状态并锁定版本 | 依赖兼容或支持周期发生变化 |
| 首个主动接入 | M0 调查团队实际可用的平台，选能取得完整对话并调用工具、显示报告的宿主 | Core 和 CLI 先行；自动收尾能力留作用户可开启的扩展 |
| 通用后备入口 | CLI 导入规范化完整对话文件 | 从第一阶段就存在，不依赖首个宿主 |
| 演示项目 | TypeScript 小型优惠券应用：Fastify API + 简单结算页面 + 临时测试数据库 | 可换框架，保留同样的需求与缺陷案例 |
| 首批支持对象 | 可在受控环境启动、有明确启动配置的本地 Web/API 项目 | 通过运行配置扩展，不能宣传任意仓库开箱即用 |
| 执行环境 | 主程序在宿主运行；被测应用及测试数据在受限 Docker 环境运行 | Docker 不可用时只做静态准备，并报告动态检查无法验证 |
| 报告载体 | CLI 摘要、结构化 JSON、可独立打开的本地 HTML 证据报告 | 宿主允许时增加原生卡片，无需先做网站 |
| 运行预算 | 初始默认总计 180 秒、单工具 60 秒、最多 4 次生成模型调用、最多 1 轮补证；均可配置 | 用实测调整；耗尽预算仍输出已有结果和缺口 |

主模型的供应商、具体模型 ID、可用凭据、可接受单次成本，以及团队实际演示宿主，需要在 M0 记录。若宿主或凭据暂时不可用，M0 明确记录缺口，先推进可独立完成的 Core/CLI 工作。环境变量传递密钥，不把密钥写入文档。不能仅凭榜单宣布模型最优；模型选择方法见验收文档。

“首个接入平台”只影响接入层，不改变跨 Agent 定位。Codex 是开发工具，不自动成为唯一支持的宿主。

## 4. 交付边界

最初文档交付不包含业务代码。随后已依据会话授权开始实施 M1，具体状态见实施记录。后续实施继续根据当时会话授权执行；已经授权的工作不重复确认。安装系统级依赖、修改宿主全局配置、对外发布等操作须说明影响，并遵守用户当时的权限要求。

实现不得接触生产数据库、真实下单、支付、发信等外部业务。验收使用测试账户和隔离数据。

## 5. 给下一轮 Codex 的启动提示

> 在此项目开始实现 VibeGuard。先读取 docs/00-README.md 以及它指向的产品、技术、实施、验收文档。先检查现有仓库和环境，再从实施计划 M0 开始，按里程碑推进。当前没有实现的功能不要宣称完成。保留原话与证据的对应关系，不以模型自报或测试退出码替代需求验收。Jev、Laya 不属于核心依赖。每阶段说明完成内容、实际验证、证据位置和剩余问题。遇到凭据、宿主能力或授权缺口，只暂停依赖它的步骤，继续能独立完成的工作。

## 6. 文档维护

- 新需求先更新产品需求，再同步技术设计和验收用例；实施计划记录影响到哪个里程碑。

- 阶段完成状态另存实施记录，不把本文中的设计说明当成完成记录。
- 对话中用户的最新明确约定优先于旧文档。发现冲突，应更新文档并解释影响。
