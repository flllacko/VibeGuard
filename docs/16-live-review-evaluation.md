这是小规模开发联调，不能据此宣传一般准确率。前 8 例的输出已经用于修正提示词，复测不算盲评；后 2 例只是提示词冻结后补充的新样本。参考答案由开发助手事先编写，用户没有逐条审定。

## 检查了什么

参考样本在 API 调用前保存，发送给模型的只有当前要求、待定问题和这一次回复，不含参考答案。程序实际经过要求审查服务处理并保存新版本，再由另一服务实例读回；不是用固定模型响应替代真实调用。

主要核对：

- 只改文件保留期，仍保留 CSV、UTF-8/BOM 及北京时间。
- 排除离线扫码能力，其余扫码要求保持；附带认可不能跳过新版确认。
- 新增扫描件原文件下载，不擅自添加权限或下载次数规则。
- 合并开演邮件提醒，保留 24 小时、购票人、座位和入口信息。
- 将投影仪型号问题归为背景，不变成产品功能。
- 不确定大小还是数量限制时保留原要求并追问。
- 解释或暂停验收不等于确认。
- 自然认可清单时，只确认理解，不制造执行证据。
- 温室样本同时修改持续时长和日报时间，保留温度阈值、短信、管理员、统计周期和掉线记录。
- 音频样本明确保留意见时，不确认整份清单，不自行改过渡时长。

复测的上传歧义例生成了两个相近的问题，属于轻微交互冗余，后续可合并展示。本轮没有为它新增业务分支。

## 实测暴露的问题与修正

1. 非操作分段漏写空 `operationIndexes`，导致有意义的输出被格式拒绝。现在缺省为空数组；真正的操作片段仍必须关联操作，来源检查没有放松。
2. 模型将保留旧条件、修改理由和真实修改混写，或给出确认却把所有片段归为背景。明确了通用输出合同，并将程序校验反馈交回模型修正，最多一次。
3. 清楚的修改后附带开始意图，不应额外制造一个没有业务歧义的问题；新版本来就需要再次展示并确认。

未增加“识别某种业务关键词就修改某条要求”的代码。修改、排除、恢复、补充、合并、澄清仍是跨业务复用的通用动作。网络、认证失败不按格式问题反复调用。

新增回归测试覆盖一次反馈修正、两次失败封顶、用量累计、非操作字段缺省，以及评估参考答案不进入模型输入。构建与 **114 项自动化测试通过**；自动化测试本身不调用付费模型。

## 如何复现

在项目构建完成、DeepSeek 凭据已配置后：

```powershell
# 只准备材料和参考答案，不调用模型。每轮使用新目录。
pnpm eval:review prepare --cases fixtures/evaluations/review-reply-live-20261018.json --out .vibeguard/evaluations/my-review-run

# 这一步才调用真实付费模型，最多每例两次。
pnpm eval:review run --manifest .vibeguard/evaluations/my-review-run/manifest.json
```

新增样本文件是 `fixtures/evaluations/review-reply-fresh-20261018.json`。不得将不同轮次覆盖到同一个目录，或修改参考答案后沿用旧报告。运行前可查看 `outgoing-review.md` 与 `outgoing-inputs.json`。

本机完整记录位于 `.vibeguard/evaluations/live-review-20261018/`：

- `first-run/`：首次原始失败、模型响应和逐例复核。
- `retest/`：同组修复复测，包括一次重试。
- `fresh-samples/`：提示词冻结后的两例补充样本。
- 每轮 `data/review-model-attempts/` 保存真实原始响应、策略标识和用量。

原始响应的 `reviewRef` 指输入的父清单；结果的 `reviewRef` 指修订后子版本。关联由清单 manifest 和子版本 `parentReviewRef` 核对，不按业务内容猜测。
